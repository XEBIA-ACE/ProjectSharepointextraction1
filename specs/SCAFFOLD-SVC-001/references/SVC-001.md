# Claims & Case Management Service

## C3 — Summary

C3 Component view for SVC-001 "Claims & Case Management Service" showing controllers, application services, domain services, repositories, integration adapters, messaging adapters, and cross-cutting components within a modular monolith, along with key external dependencies such as databases, event bus, policy/customer systems, document service, notifications, payments, and rules engine.

## C3 — Insights

- The service is structured as a modular monolith with clear subdomains (claims core, triage, investigation, fraud, settlement) each represented by an application service plus focused domain services and repositories, improving cohesion and evolution paths to microservices if needed.
- Triage & Assignment relies heavily on event-driven processing (claim.created), deterministic routing rules, and the Idempotency & Concurrency Manager to meet ordering and idempotency guarantees from F-02 stories like US-005 and US-006.
- Investigation, Fraud, and Settlement workflows share the Workflow & Case Repository but are isolated logically through their own domain services, which simplifies enforcing guarded lifecycle transitions, reopen rules, and role-based access seen in F-03 and F-04 stories.
- Cross-cutting concerns such as RBAC authorization, validation/error mapping, logging/observability, configuration, and health checks are centralized components used by all vertical slices, supporting standardized error models, correlation IDs, and auditability mandated by submission and fraud stories.
- External integrations (Policy, Customer, Doc, Notification, Payment, Rules Engine) are accessed only via dedicated client adapters, keeping the domain and application services isolated from protocol details and enabling resilience features like retries, rate limiting, and circuit breakers.
- The Domain Event Publisher and Event Consumers decouple internal workflows (auto-assignment, fraud evaluation, SLA-driven escalation) from synchronous API flows, enabling at-least-once, ordered-per-claim processing and DLQ/reprocessing patterns required by fraud and triage requirements.

## C4 — Summary

Code-level C4 view for SVC-001 (Claims & Case Management Service) focusing on submission, triage/assignment (including escalation and overrides), investigations, settlements, and fraud evaluation. The design follows a layered, DDD-oriented modular monolith in Java/Spring Boot style with explicit domain aggregates, application services, infrastructure adapters, and REST controllers. Key concerns such as idempotent processing, RBAC, optimistic concurrency/ETags, SLA/escalation behavior, deterministic auto-assignment, multi-level approvals, and fraud indicator governance are captured in targeted classes and methods rather than exhaustively modeling the entire codebase.

## C4 — Insights

- Layered structure: Presentation (controllers, exception handler) depends only on application services; application services orchestrate use cases using repositories, domain methods, and external clients; domain layer holds business rules and invariants; infrastructure provides JPA repositories, outbound clients, idempotency, rate limiting, messaging, and audit logging.
- DDD aggregates: Claim, Draft, Investigation, InvestigationTask, SettlementRecommendation, FraudEvaluation are explicit aggregates with behavior methods capturing key acceptance criteria (e.g., Claim.escalate, SettlementRecommendation.approve, Investigation.transition). This prevents anemic domain and centralizes invariants like escalation suspension of auto-routing, guarded lifecycle transitions, and read-only enforcement after final decisions.
- Triage & auto-assignment: TriageAssignmentApplicationService plus AssignmentStrategy/UtilizationAwareAssignmentStrategy, AssignmentRule, Investigator, AvailabilityClient, and IdempotencyStore implement deterministic, utilization-aware auto-assignment with rule precedence, idempotency per claim, ordered processing per claim, availability staleness checks, and UNASSIGNED_TRIAGE fallback with notifications, satisfying US-005/US-006/US-008/US-007.
- Escalation lifecycle: Claim aggregate keeps escalated flag and escalatedAtUtc in UTC; methods escalate and clearEscalation encapsulate rules such as requiring an escalation-capable investigator for claims in UNASSIGNED_TRIAGE, suspending auto-routing while escalated, enforcing supervisor RBAC (via SecurityContextAccessor), and validating timestamps, directly grounded in US-008.
- Manual and bulk assignment: TriageAssignmentApplicationService methods [REDACTED-AWS_SECRET_KEY] and supervisorOverride/bulkSupervisorOverride coordinate eligibility/availability checks via InvestigatorRepository and AvailabilityClient, enforce optimistic concurrency through Claim.version, and integrate with NotificationsClient and AuditLogger. Bulk dry-run returns validation outcomes without calling ClaimRepository.save, addressing US-006 and US-007 idempotency and conflict requirements.
- Investigation workflow: InvestigationApplicationService and Investigation aggregate plus InvestigationTask model guarded status transitions, terminal state protection, reopen with mandatory reason, If-Match/ETag concurrency, and task management whose completion feeds guard evaluation, capturing US-014–US-018 behavior while deferring task details to domain methods and guard context objects.
- Settlement approvals: SettlementRecommendation aggregate encodes Draft→Submitted→In Review→Approved/Rejected/Returned states, Preparer vs Approver roles, claim/release semantics, mandatory reasons for decisions, read-only after final decision, withdraw rules, and multi-level approval routing via currentApproverLevel/maxRequiredLevel, thus aligning with US-001–US-004 while keeping workflow logic local to the aggregate and coordinated by SettlementApplicationService.
- Fraud detection & governance: FraudEvaluationConsumer, FraudEvaluation aggregate, FraudScoringStrategy, FraudIndicatorConfigRepository, FraudEvaluationRepository, and IdempotencyStore collectively support event-driven, idempotent, per-claim ordered evaluations; indicator versioning and effective dating; incomplete evaluations with reason codes; linkage-aware scoring; and DLQ-based reprocessing from US-019–US-023 and US-021.
- Idempotency & concurrency: IdempotencyStore encapsulates 24h key retention for submissions and fraud evaluations, ensuring repeat requests/events do not create duplicate business effects; Claim.version and Draft.revision support optimistic locking with 409 responses; ETag properties on Investigation and InvestigationTask support If-Match concurrency in controllers and application services per ACs.
- Cross-cutting policies: SecurityContextAccessor centralizes RBAC checks (Supervisor, triage:assign, Preparer, Approver), RateLimiter supports submission limits and triage actions, AuditLogger records immutable audit entries for key operations, and MessagePublisher/OutboxPublisher implement the Outbox pattern for domain events like ClaimSubmittedEvent and AssignmentChangedEvent, in line with patterns P-7, P-11, and P-12.

## API specification — Summary

REST API design for SVC-001 focused on claim drafts and submission, document upload, triage queues and assignments, escalation and supervisor overrides, investigation lifecycle and tasks, fraud evaluation retrieval, and settlement recommendation submission and approval. The spec follows resource-oriented URLs, uses JSON with ISO-8601 UTC timestamps, employs optimistic concurrency with ETags and revision fields, standardizes error responses with correlation IDs, and applies JWT bearer authentication with RBAC aligned to Policyholder, Agent, Analyst, Supervisor, Investigator, Preparer, Approver, and Admin roles.

## API specification — Insights

- Kept the surface area scoped to what the user stories explicitly require: no speculative MFA, no generic CRUD for all aggregates, and no rule-authoring endpoints since governance is handled elsewhere.
- Claim submission flow separates draft mutation from submission, enabling optimistic locking, idempotent submission, rate limiting, and strong dependency error handling in line with F-01 stories.
- Triage and assignment endpoints model queues and actions (manual, bulk, escalation, override) as dedicated commands rather than generic updates, reflecting complex validation, RBAC, and idempotency semantics.
- Investigation workflow uses ETag-based optimistic concurrency on the investigation aggregate so that status transitions, assignee changes, and task changes are all guarded and auditable as required.
- Settlement APIs distinguish Preparer and Approver responsibilities with different endpoints and enforce terminal read-only behavior while supporting worklist claim/release and multi-level approvals via decision metadata.
- Fraud evaluation exposure is kept minimal for this service: a manual trigger and a read endpoint around a FraudEvaluation resource, while indicator governance and automated processing remain internal or in other services per F-04.
- Standardized ErrorResponse plus canned reusable responses (400/401/403/404/409/429/503) make the error model consistent across modules and support the observability and PII-masking requirements.
- Use of Idempotency-Key headers on claim submission and fraud evaluation, plus requestId on supervisor overrides, codifies idempotent behavior and conflict detection described in the stories.
- Pagination and filtering are only added where explicitly needed (triage and settlement worklists), with simple page/pageSize/sort parameters for predictable performance and UX.
- All time-related fields are modeled as UTC date-time strings, matching the acceptance criteria around UTC storage and local-time presentation in clients.

## API specification — Error handling

- Standardized error model with top-level { error: { code, message, correlationId, details[] } }.
- HTTP 400 for validation and business rule failures, including detailed field-level errors where relevant.
- HTTP 401 when authentication is missing or invalid; HTTP 403 when user is authenticated but lacks required role/permission.
- HTTP 404 when the requested resource (claim, draft, investigation, settlement, etc.) does not exist or is not visible to the caller.
- HTTP 409 for optimistic concurrency conflicts (ETag mismatch, outdated draftRevision), conflicting idempotency keys, or invalid state transitions such as editing read-only entities.
- HTTP 429 for rate limiting breaches on claim submission, per specified 5/min and 10/day thresholds.
- HTTP 503 when critical dependencies (Policy, Customer, Document repository, etc.) are unavailable; operations fail closed with no state change.
- All error responses include a correlationId and avoid exposing PII in messages.
