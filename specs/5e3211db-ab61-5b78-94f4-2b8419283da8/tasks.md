# Tasks: 5e3211db-ab61-5b78-94f4-2b8419283da8

- [ ] T001 FR-001 (S5-AC1): verifyOtp() SHALL, when invoked for a user_id that has an associated OTP request whose passcode is valid and not expired and whose related user account is active, and when the provided passcode matches the stored OTP code, return a success result that includes: (a) verified_at set to the current time, (b) the corresponding OTP record's verified flag set to true, and (c) outcome and error_code fields populated in the response. The criteria do not specify the exact values of outcome and error_code beyond their presence on success.
- [ ] T002 FR-002 (S5-AC2): verifyOtp() SHALL, when an OTP request exists but the corresponding user account is in a locked state and a valid passcode is supplied, return an error with HTTP-equivalent status 422 and error_code ACCOUNT_STATE_INVALID and SHALL NOT increment the OTP request's attempt_count in this scenario.
- [ ] T003 FR-003 (S5-AC3): verifyOtp() SHALL, when an OTP request exists but the corresponding user account is marked for deletion and a valid passcode is supplied, return an error with HTTP-equivalent status 422 and error_code ACCOUNT_STATE_INVALID and SHALL NOT increment the OTP request's attempt_count in this scenario. The criteria do not distinguish behavior for different deletion sub-states beyond using ACCOUNT_STATE_INVALID.
- [ ] T004 FR-004 (S5-AC4): verifyOtp() SHALL, when an OTP request exists with attempt_count equal to OTP_MAX_ATTEMPTS - 1 (default 4) and an incorrect passcode is supplied, increment attempt_count from OTP_MAX_ATTEMPTS - 1 to OTP_MAX_ATTEMPTS for that OTP request and SHALL cause the subsequent verification attempt against that same OTP request to result in a 409 OTP_LOCKED response. The criteria leave ambiguous whether the attempt that raises attempt_count to OTP_MAX_ATTEMPTS itself returns INVALID_PASSCODE or OTP_LOCKED; the implementation MUST satisfy the described state transition and next-call behavior.
- [ ] T005 FR-005 (S5-AC5): verifyOtp() SHALL, when an OTP request exists with attempt_count equal to OTP_MAX_ATTEMPTS (default 5) before processing and any passcode is supplied (correct or incorrect), return an error with HTTP-equivalent status 409 and error_code OTP_LOCKED and SHALL NOT further increment attempt_count beyond OTP_MAX_ATTEMPTS for that OTP request.
- [ ] T006 FR-006 (S5-AC6): verifyOtp() SHALL, when an OTP request exists with attempt_count strictly less than OTP_MAX_ATTEMPTS and an incorrect passcode is supplied (and the OTP is otherwise non-expired and not already locked), increment attempt_count by exactly 1 and return an error with HTTP-equivalent status 422 and error_code INVALID_PASSCODE. The criteria do not constrain whether any additional metadata (e.g., remaining attempts) is included in the response.
- [ ] T007 FR-007 (S5-AC7): verifyOtp() SHALL, when an OTP request exists with attempt_count strictly less than OTP_MAX_ATTEMPTS and a correct passcode is supplied, perform the passcode comparison using Node.js crypto.timingSafeEqual (or an equivalent timing-safe operation) between the provided passcode and the stored OTP code, and SHALL NOT use non-constant-time comparison for this decision. The criteria do not prescribe the exact encoding/normalization used before comparison, only that crypto.timingSafeEqual is used.
- [ ] T008 FR-008 (S5-AC8): verifyOtp() SHALL, when called for a user_id for which no corresponding OTP request exists (e.g., no pending OTP or no record for that user), return an error with HTTP-equivalent status 404 and an appropriate error response body. The criteria do not specify the exact error_code or message text, only that the response is a 404 indicating missing OTP.
- [ ] T009 FR-009 (S5-AC9): verifyOtp() SHALL, when an OTP request exists but is in an expired state and the supplied passcode is correct, return an error with HTTP-equivalent status 410 and error_code EXPIRED_OTP (or equivalent identifier for expired OTP) instead of treating the OTP as valid; the requirement does not mandate any change to attempt_count in this scenario and is silent on whether any other fields are updated.
- [ ] T010 FR-010 (S5-AC10): verifyOtp() SHALL, when an OTP request exists but is in an expired state and an incorrect passcode is supplied, return an error with HTTP-equivalent status 410 representing EXPIRED_OTP and SHALL NOT increment attempt_count for that OTP request in this scenario, regardless of the incorrect passcode. The criteria do not specify whether any other side effects (such as logging) occur.

- [ ] T015 Verify S5-AC5: Given an OTP request exists with attempt_count at OTP_MAX_ATTEMPTS (default 5), when verifyOtp() is called with any passcode, then the method returns 409 OTP_LOCKED without further incrementing attempt_count.
